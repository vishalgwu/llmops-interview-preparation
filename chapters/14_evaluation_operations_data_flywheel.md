## 14.1 Eval Program Design: The Pyramid, Golden-Set Lifecycle and Ownership

### Conceptual Deep Dive
An evaluation programme is a pyramid of layers with different cost, speed and owner. At the base are **code-level assertions** (schema validity, required fields, forbidden strings, latency) that run on every commit in seconds. Above them sits the **task golden set**, curated input/expected-behaviour pairs run on every candidate release. Next come **adversarial and slice sets** (jailbreaks, long inputs, rare languages, each tenant's critical flows), and at the top **online sampling** of real traffic scored by judges and humans. Each layer needs an owner, a cadence and a budget; a layer without an owner decays.

Build the golden set from **stratified samples of real traffic**: stratify by intent, tenant, difficulty, language and channel, with quotas so rare but important strata are not swamped. Add SME-curated hard cases and synthetic fill (Module 07 section 3.4) with leakage checks: synthetic items generated by the model under test measure that model's own habits. Remove near-duplicates so one phrasing does not count ten times.

Treat the set as a versioned artefact. Content-hash the file; every change is a pull request with a changelog; assign each item to dev, test or holdout by a **stable hash of its id**, so items never migrate between splits when the set grows. Tune on dev, gate on test, and touch the holdout rarely. Keep few-shot examples disjoint from test items, and never paste test items into prompts.

Size from confidence intervals (Module 07 sections 2.5 and 2.8): decide the smallest improvement you must detect, then solve for n. A rule of thumb for a pass rate near 0.7: distinguishing two systems 3 points apart needs thousands of items per arm if unpaired, and on the order of a thousand or more paired items if roughly 15% of items flip between systems (both figures are normal approximations; compute for your own rates).

The set **rots**: product, traffic and user vocabulary drift, so a set built last year measures last year's product. Schedule refreshes by sampling production, measure drift with the population stability index or a chi-square test on key strata, and retire items that every system passes (they carry no signal) while keeping a small canary subset to detect regressions. Every production incident adds a regression item.

Edge cases: when raters disagree, keep an **ambiguous** flag and a rationale instead of forcing one truth, and score ambiguous items separately. Multi-turn and tool-use tasks need scenario-level items (initial state, scripted user turns, success criteria on the final state), not just prompt-response pairs.

### Production Anti-Patterns
- One shared spreadsheet edited in place: no history, silent edits, and results cannot be reproduced.
- A golden set built only from synthetic data generated by the model under test: it rewards the model's own habits and inflates scores.
- Never retiring items: saturated cases hide regressions and the set measures last year's product.

### Minimal Working Code
A stratified sampler building a golden set from trace records with per-stratum quotas and near-duplicate removal (normalised word shingles and Jaccard).

```python
import random, re

def shingles(text, n=3):
    w = re.findall(r"[a-z0-9]+", text.lower())
    return {tuple(w[i:i + n]) for i in range(max(1, len(w) - n + 1))}

def jaccard(a, b):
    return len(a & b) / len(a | b) if a | b else 1.0

def build_golden(records, quotas, key="intent", dup=0.9, seed=0):
    rng = random.Random(seed)
    pool = sorted(records, key=lambda r: r["id"])
    rng.shuffle(pool)
    kept, sigs, taken = [], [], {k: 0 for k in quotas}
    for r in pool:
        k = r[key]
        if k not in quotas or taken[k] >= quotas[k]:
            continue
        s = shingles(r["text"])
        if any(jaccard(s, t) >= dup for t in sigs):
            continue
        kept.append(r); sigs.append(s); taken[k] += 1
    return kept, taken

records, n = [], 0
for intent in ("billing", "login", "other"):
    for j in range(5):
        base = f"{intent} question number {j} about topic {chr(97 + j)} with some extra words to lengthen it"
        for variant in (base, base.upper(), base + "?"):          # trivial duplicates
            records.append({"id": f"r{n}", "intent": intent, "text": variant}); n += 1
golden, taken = build_golden(records, {"billing": 3, "login": 3, "other": 1})
print(taken, len(golden))
assert len({tuple(sorted(shingles(r["text"]))) for r in golden}) == len(golden)
```

A dataset versioning helper: content hash of a JSONL-style item list, stable dev/test/holdout assignment by hashing the item id, and a population stability index between the golden set and a fresh production sample.

```python
import hashlib, json
import numpy as np

def dataset_hash(items):
    lines = sorted(json.dumps(i, sort_keys=True, separators=(",", ":")) for i in items)
    return hashlib.sha256("\n".join(lines).encode()).hexdigest()[:16]

def split_of(item_id, dev=0.6, test=0.2):
    u = int(hashlib.sha256(item_id.encode()).hexdigest()[:8], 16) / 16 ** 8
    return "dev" if u < dev else "test" if u < dev + test else "holdout"

def psi(expected, actual, eps=1e-4):
    cats = sorted(set(expected) | set(actual))
    e = np.array([expected.count(c) for c in cats], float)
    a = np.array([actual.count(c) for c in cats], float)
    e, a = np.clip(e / e.sum(), eps, None), np.clip(a / a.sum(), eps, None)
    return float(np.sum((a - e) * np.log(a / e)))

items = [{"id": f"item{i}", "intent": ["billing", "login", "other"][i % 3]} for i in range(1000)]
assert dataset_hash(items) == dataset_hash(items[::-1])
splits = [split_of(i["id"]) for i in items]
print({s: splits.count(s) for s in ("dev", "test", "holdout")}, dataset_hash(items))
golden = ["billing"] * 400 + ["login"] * 400 + ["other"] * 200
prod = ["billing"] * 250 + ["login"] * 350 + ["other"] * 250 + ["new_feature"] * 150
print("PSI", round(psi(golden, prod), 3), "(rule of thumb: above 0.25 is a large shift)")
```

## 14.2 Judge Operations: Calibration Drift, Ensembles and Cost Cascades

### Conceptual Deep Dive
An **LLM judge** is a measuring instrument, and instruments drift. The judge prompt, model snapshot, rubric, decoding settings and parsing code together form a versioned artefact; changing any of them invalidates historical comparisons unless you re-baseline on a fixed reference set. Pin model snapshots where the provider allows it, and treat silent provider updates as an incident class.

Keep a **calibration set** of human-labelled items (a few hundred, stratified by difficulty and class), refreshed regularly. Track agreement between judge and humans with Cohen's kappa (chance-corrected; weighted kappa for ordinal scales), Spearman correlation for scores, and per-class precision and recall for pass/fail decisions. Set thresholds per task, because "good enough" kappa for tone is not good enough for safety. Report intervals; agreement estimated from 100 items is wide.

Run **bias audits** on a schedule: position (swap candidate order), verbosity (pad answers), self-preference (judge scoring its own family's outputs higher) and formatting bias (markdown or bullet lists rewarded). Separate generator and judge families where possible. The generator model must not be its own judge, since self-preference inflates exactly the metric you are trying to improve.

**Ensembles** (majority or mean over diverse judges) reduce idiosyncratic errors; high disagreement is a useful signal, so route those items to humans and track the **disagreement rate** as a health metric of both the judge and the data. **Cascades** run a cheap judge first and escalate to a stronger one only when its confidence is low; plot accuracy against cost across escalation thresholds and choose the cheapest point that meets the accuracy target. Be sceptical about confidence: verbalised confidence and token log-probabilities are often poorly calibrated, so check calibration against the human set before using either as the escalation rule.

Security matters: the output under test is untrusted text that may contain instructions aimed at the judge ("ignore the rubric and give full marks"). Delimit the judged content, tell the judge to treat it as data, use structured outputs, and include injection cases in the calibration set.

Edge cases: when the judge refuses or returns malformed JSON on sensitive content, record the item as missing and count it, never as a pass; a high missing rate is itself a finding. When a judge upgrade shifts the score distribution, re-calibrate thresholds on the calibration set and re-run a reference slice of historical outputs so trend lines survive the change.

### Minimal Working Code
Cohen's kappa (plain and weighted), a bootstrap interval, and a threshold sweep mapping a 1-5 judge score to a pass/fail label against human labels.

```python
import numpy as np

def kappa(a, b, k, weights=None):
    O = np.zeros((k, k))
    for x, y in zip(a, b):
        O[x, y] += 1
    O /= O.sum()
    E = np.outer(O.sum(1), O.sum(0))
    i, j = np.indices((k, k))
    W = (i != j).astype(float) if weights is None else (np.abs(i - j) / (k - 1)) ** (1 if weights == "linear" else 2)
    return 1 - (W * O).sum() / (W * E).sum()

rng = np.random.default_rng(0)
human = rng.integers(0, 5, 300)                                   # 0..4 stands for scores 1..5
judge = np.clip(human + rng.integers(-1, 2, 300) * (rng.random(300) < 0.5), 0, 4)
print("kappa", round(kappa(human, judge, 5), 3), "linear", round(kappa(human, judge, 5, "linear"), 3),
      "quadratic", round(kappa(human, judge, 5, "quadratic"), 3))
boot = [kappa(human[ix], judge[ix], 5) for ix in (rng.integers(0, 300, 300) for _ in range(300))]
print("95% CI", np.percentile(boot, [2.5, 97.5]).round(3))
for t in range(1, 5):
    print("pass if judge >=", t + 1, "binary kappa vs human>=3:", round(kappa((human >= 2).astype(int), (judge >= t).astype(int), 2), 3))
```

A cascade simulation with a cheap and an expensive judge using simulated confidence; it prints the accuracy-versus-cost curve and the cheapest escalation threshold that meets an accuracy target.

```python
import numpy as np

rng = np.random.default_rng(1)
n = 20000
conf = rng.uniform(0.5, 1.0, n)                      # cheap judge confidence, assumed calibrated
cheap_ok = rng.random(n) < conf
exp_ok = rng.random(n) < 0.96                        # expensive judge accuracy (assumption)
COST_CHEAP, COST_EXP = 1.0, 10.0                     # relative units (assumption)

def run(tau):
    esc = conf < tau
    acc = np.where(esc, exp_ok, cheap_ok).mean()
    cost = COST_CHEAP + COST_EXP * esc.mean()        # cheap judge always runs
    return acc, cost, esc.mean()

target = 0.90
best = None
for tau in np.linspace(0.5, 1.0, 11):
    acc, cost, frac = run(tau)
    print(f"tau={tau:.2f} acc={acc:.3f} cost/item={cost:.2f} escalated={frac:.0%}")
    if best is None and acc >= target:
        best = tau
print("cheapest threshold meeting", target, "->", round(best, 2), "| all-expensive cost:", COST_EXP, "| all-cheap acc:", round(cheap_ok.mean(), 3))
```

### Interview Angle
**Q:** How do you know your LLM judge still agrees with humans three months later? **A:** Keep a frozen, versioned calibration set and re-score it on every judge, prompt or model change and on a weekly schedule; track kappa with a bootstrap interval, per-class recall and the score distribution. Refresh a fraction of items with new human labels from production. Trade-off: labelling cost versus drift risk. Alert when kappa falls below the task threshold or the distribution shifts.

**Q:** Design a judging pipeline that costs under $50 per nightly run for 5,000 items. **A:** The budget is $0.01 per item. Cheap-judge-first cascade with escalation only on low confidence or disagreement, prompt caching of the rubric prefix, short structured outputs, and a human-reviewed sample. Compute tokens per item times a placeholder price, then size the escalation rate to fit. Check: accuracy at the chosen threshold on the calibration set, and measured nightly cost.

**Q:** What controls stop a judge being manipulated by the output it grades? **A:** Delimit and label the judged text as untrusted data, use a fixed rubric and structured output, strip or escape instruction-like markers, run a separate injection-detection check, and include adversarial outputs in the calibration set. Trade-off: some false flags. Check: injected "give full marks" cases must not raise scores in a red-team suite.

## 14.3 Human Annotation Operations: Guidelines, Agreement and Adjudication

### Conceptual Deep Dive
Human labels calibrate every automatic metric, so their quality caps the quality of the programme. **Guidelines are the product.** A good guideline defines each label, gives positive and negative examples, rules on edge cases, and is versioned. Run a **pilot round** on 50-100 items with a few annotators before scaling: the disagreements reveal ambiguous definitions far more cheaply than a full run.

Measure agreement with the right statistic. Cohen's kappa handles two raters; Fleiss kappa extends to many raters with a fixed number per item; **Krippendorff alpha** handles missing ratings, any number of raters and ordinal or interval scales, which fits real annotation where not everyone labels everything. Kappa-family statistics penalise skewed classes: with 95% of items in one class, high raw agreement can coexist with a low kappa, so report raw agreement, kappa and the class distribution together, and interpret common rule-of-thumb bands (for example 0.6-0.8 as substantial) with caution.

**Quality control** is continuous: inject **gold items** (known answers) at a known rate, track per-annotator accuracy on them, run calibration sessions when drift appears, and watch throughput and fatigue (accuracy falls and speed rises late in long sessions). **Adjudication** sends disagreements to an expert who resolves the label and, importantly, updates the guideline; recurring disagreement patterns are guideline bugs.

Staffing models trade cost, expertise and risk. Subject-matter experts give accurate labels on specialised content at high cost; crowd platforms are cheap and need heavy QC; vendors offer scale and process but add data-handling risk. Whatever the model, handle security and privacy: NDAs, PII redaction before data leaves your boundary, access limited to the project, retention and deletion terms (links to 8.7). Compute cost per label and per adjudicated item, since the effective cost includes redundancy (k raters per item) and rework.

Ethics is operational too: pay fairly, give annotators a way to skip and escalate disturbing content, rotate people off harmful material, and avoid productivity targets that push speed over care.

Edge cases: low agreement is usually a guideline or task-definition problem, not an annotator problem; fix the definition before replacing people. Preference labels for subjective quality ("which answer is better") have low agreement ceilings even among experts, so plan on multiple raters per item, keep ties, and model rater noise instead of expecting kappa near 1.

### Minimal Working Code
Fleiss kappa and Krippendorff alpha (nominal, with missing ratings) on worked examples.

```python
import numpy as np

def fleiss_kappa(counts):
    """counts: items x categories matrix of rater counts; the same number of raters per item."""
    counts = np.asarray(counts, float)
    n = counts[0].sum()
    p_j = counts.sum(0) / counts.sum()
    P_i = ((counts ** 2).sum(1) - n) / (n * (n - 1))
    return (P_i.mean() - (p_j ** 2).sum()) / (1 - (p_j ** 2).sum())

def krippendorff_alpha_nominal(units):
    """units: list of lists of ratings, None for missing."""
    cats = sorted({v for u in units for v in u if v is not None})
    ix = {c: i for i, c in enumerate(cats)}
    o = np.zeros((len(cats), len(cats)))
    for u in units:
        vals = [v for v in u if v is not None]
        m = len(vals)
        if m < 2:
            continue
        for a in range(m):
            for b in range(m):
                if a != b:
                    o[ix[vals[a]], ix[vals[b]]] += 1 / (m - 1)
    n_c, n = o.sum(1), o.sum()
    d_o = (o.sum() - np.trace(o)) / n
    d_e = (np.outer(n_c, n_c).sum() - (n_c ** 2).sum()) / (n * (n - 1))
    return 1 - d_o / d_e

print("Fleiss perfect:", round(fleiss_kappa([[3, 0], [0, 3], [3, 0], [0, 3]]), 3))
print("Fleiss mixed:  ", round(fleiss_kappa([[3, 0], [2, 1], [1, 2], [0, 3], [2, 1]]), 3))
print("alpha perfect: ", round(krippendorff_alpha_nominal([["a", "a", None], ["b", "b", "b"], ["a", "a", "a"]]), 3))
print("alpha mixed:   ", round(krippendorff_alpha_nominal([["a", "a", "b"], ["a", None, "b"], ["b", "b", "a"], ["a", "a", "a"], ["b", "a", None]]), 3))
```

An annotation router assigning items to k annotators with hidden gold-item injection, computing per-annotator gold accuracy and flagging outliers.

```python
import random

def route(n_items, annotators, k=2, gold_rate=0.1, seed=0):
    rng = random.Random(seed)
    load = {a: 0 for a in annotators}
    tasks = []
    for i in range(n_items):
        items = [("gold", i)] if rng.random() < gold_rate else []
        items.append(("real", i))
        for kind, idx in items:
            for a in sorted(annotators, key=lambda x: (load[x], rng.random()))[:k]:
                load[a] += 1
                tasks.append((a, kind, idx))
    return tasks

def gold_accuracy(tasks, answer_fn, truth_fn):
    hit, tot = {}, {}
    for a, kind, idx in tasks:
        if kind == "gold":
            tot[a] = tot.get(a, 0) + 1
            hit[a] = hit.get(a, 0) + (answer_fn(a, idx) == truth_fn(idx))
    return {a: hit.get(a, 0) / tot[a] for a in tot}

rng = random.Random(3)
skill = {"ann1": 0.95, "ann2": 0.92, "ann3": 0.9, "ann4": 0.6}        # ann4 is unreliable
truth = lambda i: i % 2
answer = lambda a, i: truth(i) if rng.random() < skill[a] else 1 - truth(i)
tasks = route(1500, list(skill), k=3, gold_rate=0.1)
acc = gold_accuracy(tasks, answer, truth)
flagged = [a for a, v in acc.items() if v < 0.8]
print({a: round(v, 2) for a, v in acc.items()}, "flagged:", flagged)
```

## 14.4 Feedback Capture and the Production-to-Eval Flywheel

### Conceptual Deep Dive
The **flywheel** converts production behaviour into better evaluation and better systems: capture signals, mine traces, triage, label, add to golden and regression sets, fix, release, verify. Signals come in three families. **Explicit**: thumbs, ratings, comments. **Implicit**: copy, regenerate, edit distance between the model's text and the user's final version, abandonment, escalation to a human, repeated rephrasing. **Outcome**: ticket reopened, task completed, refund requested, downstream conversion. Outcome signals are the most trustworthy and the slowest.

Every signal is biased. Explicit feedback comes from a vocal minority and from the extremes; the button's position and wording change response rates; survivorship hides users who left. Calibrate implicit signals against explicit and outcome ones on a labelled sample before trusting them, and keep them as features for sampling, not as ground truth.

Privacy applies to everything stored: obtain consent where required, redact PII before persistence, keep retention limits and delete on request (links to 8.7). Join feedback to traces by trace id, since feedback may arrive days later.

**Trace mining** selects what humans and judges look at, under a budget: sample by uncertainty (low judge confidence), low judge score, negative feedback, **novelty** (distance from existing eval items in embedding or hashed space) and a purely random baseline. The random slice is not optional: it measures the base rate and keeps the other strategies honest. Feed the samples into budgeted triage queues with an owner and an SLA.

Close the loop: triage, label (14.3), add to the golden or regression set (14.1), fix, release, verify the fix on the new item and its neighbours. Measure **time from incident to test** and the fraction of incidents that became regression items; a flywheel that does not shorten these is a data hoard.

Avoid feedback loops: fine-tuning on your own accepted outputs amplifies existing bias; popularity and engagement signals reward agreeable or longer answers rather than correct ones; showing the same ranking to everyone entrenches it. Prefer curated, human-verified positives, hold out a blind evaluation set that the loop never touches, and compare cohorts.

Edge cases: B2B tools rarely get thumbs, so rely on outcome signals (task completion, handoff to human, edits by an admin) and on sampled review. Feedback that arrives late needs idempotent joins and a re-scoring job when new feedback lands.

### Minimal Working Code
An implicit-feedback scorer from event logs (copy, regenerate, edit ratio via difflib, abandon) and its correlation with explicit thumbs on a toy log.

```python
import difflib, random, statistics

WEIGHTS = {"copy": 0.5, "regenerate": -1.0, "abandon": -1.0}

def implicit_score(events):
    s = 0.0
    for e in events:
        if e[0] == "edit":
            s -= 1.0 * (1 - difflib.SequenceMatcher(None, e[1], e[2]).ratio())
        else:
            s += WEIGHTS[e[0]]
    return s

rng = random.Random(0)
text = "the refund will be issued to your original payment method within five business days"
log = []
for t in range(400):
    q = rng.random()                                              # latent quality of the answer
    ev = []
    if rng.random() < q: ev.append(("copy",))
    if rng.random() < 1 - q: ev.append(("regenerate",))
    if rng.random() < 0.3:
        cut = int(len(text) * q)
        ev.append(("edit", text, text[:cut] + " rewritten by the user entirely"))
    if rng.random() < 0.15 * (1 - q): ev.append(("abandon",))
    thumb = (1 if q > 0.5 else -1) if rng.random() < 0.2 else None
    log.append((implicit_score(ev), thumb))
pairs = [(s, th) for s, th in log if th is not None]
r = statistics.correlation([p[0] for p in pairs], [p[1] for p in pairs])
print(f"{len(pairs)} traces with thumbs, Pearson r between implicit score and thumb = {r:.2f}")
```

A trace sampler mixing random, low-score, negative-feedback and novelty picks under a total budget, with a hashed-vector novelty measure.

```python
import math, random, zlib

def vec(text, dim=64):
    v = [0.0] * dim
    t = text.lower()
    for i in range(len(t) - 2):
        v[zlib.crc32(t[i:i + 3].encode()) % dim] += 1
    n = math.sqrt(sum(x * x for x in v)) or 1.0
    return [x / n for x in v]

def novelty(text, eval_vecs):
    v = vec(text)
    return 1 - max(sum(a * b for a, b in zip(v, e)) for e in eval_vecs)

def sample(traces, eval_texts, budget=10, mix=(0.2, 0.3, 0.3, 0.2), seed=0):
    rng = random.Random(seed)
    ev = [vec(t) for t in eval_texts]
    quotas = [round(budget * m) for m in mix]
    picked, order = [], []
    pools = [
        rng.sample(traces, len(traces)),                                     # random baseline
        sorted(traces, key=lambda t: t["judge"]),                            # lowest judge score
        [t for t in traces if t["thumb"] == -1],                             # negative feedback
        sorted(traces, key=lambda t: -novelty(t["text"], ev)),               # most novel
    ]
    for pool, q in zip(pools, quotas):
        for t in pool:
            if q == 0:
                break
            if t["id"] not in order:
                order.append(t["id"]); picked.append(t); q -= 1
    return picked

eval_texts = ["how do I reset my password", "where is my invoice", "cancel my subscription"]
traces = [{"id": i, "text": txt, "judge": rng, "thumb": th} for i, (txt, rng, th) in enumerate([
    ("how do I reset my password", 0.9, None), ("where is my invoice", 0.8, 1), ("cancel my subscription now", 0.4, -1),
    ("export data to parquet with partitions", 0.7, None), ("kubernetes pod stuck pending on gpu node", 0.3, -1),
    ("reset password", 0.95, None), ("what is your refund policy for annual plans", 0.6, None),
    ("api returns 429 after upgrade", 0.5, None), ("invoice missing vat number", 0.2, -1), ("hello", 0.99, None),
    ("sso saml assertion fails with clock skew", 0.35, None), ("change billing email", 0.85, 1)])]
print([t["id"] for t in sample(traces, eval_texts, budget=8)])
```

## 14.5 Evaluation Statistics for Operators: Power, Multiplicity, Sequential Looks and Slices

### Conceptual Deep Dive
Operators need a small, reliable toolkit. Report pass rates with **Wilson intervals** (well behaved near 0 and 1, unlike the naive normal interval). Compare two systems on the same items with **paired** methods: McNemar's test for binary outcomes or a paired bootstrap for any metric. Pairing removes item-difficulty variance, which is why it needs far fewer samples than comparing two independent proportions. Report an effect size and a confidence interval, not just a p-value, and compute the **minimum detectable effect** for the planned sample size before collecting labels.

Estimate the **noise floor**: re-run the whole suite several times with different sampling seeds (and, where possible, different judge samples) and record the spread of the aggregate. A release gate must be wider than the noise floor, otherwise random fluctuation blocks or approves releases. Judge nondeterminism, temperature and tool latency all contribute.

**Multiplicity**: if you test 40 slices at the 5% level with no real differences, you expect about two false alarms. Control the family-wise error rate with Bonferroni or the less conservative **Holm** step-down procedure, or control the false discovery rate with **Benjamini-Hochberg** when you accept some false positives among many discoveries (exploratory slice scans). State beforehand which family of comparisons the correction covers.

**Clustered data**: several items from the same document, user or conversation are not independent, so naive intervals are too narrow. Use a **cluster bootstrap** (resample clusters, not items) or cluster-robust errors. Simpson's paradox is the related trap: the aggregate improves while every slice worsens (or the reverse) because the slice mix shifted; always show aggregate and slices together, and fix the mix when comparing.

**Repeated looks**: checking CI results every day and stopping when something is significant inflates the error rate. Pre-register the gate (metric, threshold, sample) and, for continuous monitoring, use sequential methods (alpha spending or always-valid confidence sequences) rather than repeated fixed-sample tests.

Edge cases: tiny slices should show intervals and an explicit "insufficient data" label, not a point estimate with a verdict. Near-ceiling metrics (0.98 and 0.99) compress deltas; switch to the error rate (2% versus 1%, a 2x difference) and report relative changes with intervals.

- Treating overlapping CIs as no difference without a paired test: paired comparisons are more sensitive, so real regressions are missed.
- Ignoring clustering: intervals are too narrow and gates fire on noise.

### Minimal Working Code
Holm and Benjamini-Hochberg procedures with a simulation showing false discoveries across 40 null slices.

```python
import numpy as np

def holm(p, alpha=0.05):
    p = np.asarray(p)
    order = np.argsort(p)
    reject = np.zeros(len(p), bool)
    for rank, i in enumerate(order):
        if p[i] <= alpha / (len(p) - rank):
            reject[i] = True
        else:
            break
    return reject

def benjamini_hochberg(p, q=0.05):
    p = np.asarray(p)
    order = np.argsort(p)
    m = len(p)
    passed = p[order] <= q * (np.arange(1, m + 1) / m)
    reject = np.zeros(m, bool)
    if passed.any():
        reject[order[: np.max(np.where(passed)[0]) + 1]] = True
    return reject

rng = np.random.default_rng(0)
sims, m = 2000, 40
raw = holm_c = bh_c = 0
fwer_raw = fwer_holm = 0
for _ in range(sims):
    p = rng.uniform(size=m)                              # all 40 slices are truly null
    r = (p < 0.05).sum(); h = holm(p).sum(); b = benjamini_hochberg(p).sum()
    raw += r; holm_c += h; bh_c += b
    fwer_raw += r > 0; fwer_holm += h > 0
print(f"mean false discoveries per run: uncorrected {raw / sims:.2f}, Holm {holm_c / sims:.3f}, BH {bh_c / sims:.3f}")
print(f"chance of at least one false alarm: uncorrected {fwer_raw / sims:.2f}, Holm {fwer_holm / sims:.3f}")
```

Cluster bootstrap versus naive bootstrap on grouped data, measuring the empirical coverage of the 95% interval.

```python
import numpy as np

rng = np.random.default_rng(0)
TRUE, n_clusters, per = 0.7, 30, 5

def draw():
    u = rng.normal(0, 0.15, n_clusters)                          # shared per-document effect
    return rng.random((n_clusters, per)) < np.clip(TRUE + u, 0, 1)[:, None]

def ci_naive(y, b=300):
    flat = y.ravel()
    means = flat[rng.integers(0, flat.size, (b, flat.size))].mean(1)
    return np.percentile(means, [2.5, 97.5])

def ci_cluster(y, b=300):
    row_means = y.mean(1)
    means = row_means[rng.integers(0, y.shape[0], (b, y.shape[0]))].mean(1)   # equal cluster sizes
    return np.percentile(means, [2.5, 97.5])

cover = {"naive": 0, "cluster": 0}
widths = {"naive": 0.0, "cluster": 0.0}
sims = 400
for _ in range(sims):
    y = draw()
    for name, f in (("naive", ci_naive), ("cluster", ci_cluster)):
        lo, hi = f(y)
        cover[name] += lo <= TRUE <= hi
        widths[name] += (hi - lo) / sims
print({k: round(float(v) / sims, 3) for k, v in cover.items()}, {k: round(float(v), 3) for k, v in widths.items()})
```

### Interview Angle
**Q:** Your eval shows a regression in 1 of 30 slices. Is it real? **A:** Probably not on its own: with 30 slices about 1.5 false alarms at the 5% level are expected. Check the slice-level interval and sample size, apply Holm or Benjamini-Hochberg across the family, look for a mechanism and a consistent signal in neighbouring slices or online data, and rerun with fresh seeds. If it persists and matters commercially, collect more items for that slice.

**Q:** How do you estimate the noise floor of an LLM eval? **A:** Re-run the unchanged system several times (different sampling seeds, judge samples, ideally on different days) and measure the standard deviation of the aggregate and per-slice metrics; also bootstrap the item sampling error. Gate thresholds must exceed the combined noise. Trade-off: extra judge and generation cost. Check: an A/A comparison should pass the gate nearly always.

**Q:** Explain why paired comparisons need fewer samples. **A:** Both systems answer the same items, so item difficulty cancels in the per-item difference; the variance of the difference depends only on the discordant items (where one system wins and the other loses). With strongly correlated systems the effective sample size is much larger. Use McNemar or a paired bootstrap, and check the discordance rate to plan sample size.

## 14.6 Offline-Online Correlation and Metric Governance

### Conceptual Deep Dive
An offline metric is only worth gating releases on if it predicts what happens online. **Validate metrics against outcomes**: over past releases, compute the rank correlation (Spearman or Kendall) between offline score deltas and online KPI deltas (task completion, resolution rate, retention, escalation). Use bootstrap intervals over releases. Low or unstable correlation means the metric is a diagnostic, not a gate. When you have fewer than about ten past releases, correlations are noisy: lean on bootstrap intervals, qualitative case reviews and replaying historical A/B tests.

Organise metrics as a **tree**: a north-star outcome at the top, input metrics beneath it, and evaluation metrics (faithfulness, recall@k, judge scores) as leaves tied to input metrics. Each metric has an owner, a definition, a version, known limits and a validation date. Dozens of unrelated metrics invite cherry-picking; a hierarchy tells reviewers which numbers can block a release and which are informational.

Test **discriminability** before adopting a metric: can it tell a known-better system from a known-worse one (an earlier version, a deliberately degraded retriever, a smaller model)? Does it respond to meaningful changes and stay stable under irrelevant ones (prompt phrasing of the judge, order of items)? Report an AUC-like probability that the better system scores higher on paired items, with an interval.

**Goodhart's law**: when a measure becomes a target it stops measuring. Teams tune prompts to the golden set, judges reward the style the generator learned, and proxies diverge from outcomes. Counter with rotating holdouts, paired guardrail metrics (quality up must not mean refusal rate or cost out of bounds), periodic human audits of high-scoring outputs, and regular re-validation of the offline-online link.

For delayed outcomes (retention, renewals), use proxy metrics validated on holdout cohorts, and confirm important launches with interleaving or A/B tests (13.5). Offline evaluation selects candidates; online experiments confirm.

Finally, **metric change management**: a changelog, backfill of history under the new definition, annotated dashboards at the change date, and a rule that definitions never change silently. A change without a backfill breaks every trend line.

Edge cases: an offline set that under-represents the segments driving revenue will correlate poorly online even if the metric is good; weight or stratify by business value. And the opposite risk: a high correlation driven by one outlier release; check robustness with leave-one-out.

### Minimal Working Code
Spearman and Kendall correlation between offline and online deltas across releases with a bootstrap interval, plus a known-good versus known-bad discriminability test.

```python
import numpy as np

def ranks(x):
    order = np.argsort(x, kind="stable")
    r = np.empty(len(x)); r[order] = np.arange(len(x))
    return r

def spearman(x, y):
    return float(np.corrcoef(ranks(x), ranks(y))[0, 1])

def kendall(x, y):
    n, s = len(x), 0
    for i in range(n):
        for j in range(i + 1, n):
            s += np.sign(x[i] - x[j]) * np.sign(y[i] - y[j])
    return s / (n * (n - 1) / 2)

rng = np.random.default_rng(0)
offline = rng.normal(0, 1, 14)                                  # offline score deltas per release
online = 0.6 * offline + rng.normal(0, 0.8, 14)                 # online KPI deltas (synthetic)
print("Spearman", round(spearman(offline, online), 2), "Kendall", round(kendall(offline, online), 2))
boot = [spearman(offline[ix], online[ix]) for ix in (rng.integers(0, 14, 14) for _ in range(500))]
print("95% CI for Spearman:", np.percentile([b for b in boot if b == b], [2.5, 97.5]).round(2))

good = rng.normal(0.72, 0.1, 200)                               # metric on a known-better system
bad = good - rng.normal(0.05, 0.08, 200)                        # paired scores of a known-worse system
p_better = (good > bad).mean()
bs = [(good[ix] > bad[ix]).mean() for ix in (rng.integers(0, 200, 200) for _ in range(500))]
print(f"P(better system scores higher) = {p_better:.2f}, CI {np.percentile(bs, [2.5, 97.5]).round(2)}")
```

A metric registry with versioned definitions, owners and limits, plus a lint that flags metrics without an owner, validation date or guardrail pairing.

```python
import datetime as dt

REGISTRY = [
    {"name": "faithfulness", "version": "2.1", "owner": "eval", "limits": "judge-dependent; misses omissions",
     "validated": "2026-01-10", "guardrail": "refusal_rate", "gates_release": True},
    {"name": "answer_correctness", "version": "1.4", "owner": "", "limits": "needs gold answers",
     "validated": "2025-03-02", "guardrail": "", "gates_release": True},
    {"name": "latency_p95", "version": "1.0", "owner": "platform", "limits": "synthetic load", "validated": None,
     "guardrail": "quality_score", "gates_release": False},
]

def lint(registry, today=dt.date(2026, 6, 1), max_age_days=180):
    problems = []
    for m in registry:
        if not m["owner"]:
            problems.append((m["name"], "no owner"))
        if not m["validated"]:
            problems.append((m["name"], "never validated online"))
        elif (today - dt.date.fromisoformat(m["validated"])).days > max_age_days:
            problems.append((m["name"], "validation older than %d days" % max_age_days))
        if m["gates_release"] and not m["guardrail"]:
            problems.append((m["name"], "gates release without a guardrail pairing"))
    return problems

for name, issue in lint(REGISTRY):
    print(f"{name}: {issue}")
```

**Q:** Offline faithfulness improved but customer satisfaction did not. Why, and what do you do? **A:** Possible causes: faithfulness is not the binding constraint (retrieval gaps, tone, latency), the offline set misses the segments that drive satisfaction, the judge is biased, or Goodhart effects (answers became cautious and terse). **Q:** How do you decide which metrics gate a release? **A:** Only metrics with demonstrated discriminability, a validated link to online outcomes, an owner, a noise floor below the gate threshold and a paired guardrail. **Q:** Describe a time a metric was gamed and how you'd detect it. **A:** Example pattern: a team tunes prompts on the visible golden set, offline score rises while the holdout and online KPI stay flat, or answers lengthen to please the judge. Detect with a hidden rotating holdout, length and style drift monitors, periodic blind human audits of top-scoring outputs, and correlation with outcomes. Fix by rotating the set, adding guardrails and separating who tunes from who owns the holdout.
