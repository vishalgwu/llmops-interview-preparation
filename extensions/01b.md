## 1.6 LLMOps Maturity Model and Team Topology

### Conceptual Deep Dive
A maturity model is useful only when each level has an observable exit criterion. **L0**: prompts live in notebooks and chat threads; nothing is reproducible. **L1**: prompts and configs are in Git, with basic tracing, so you can answer "what ran?". **L2**: an eval-gated CI pipeline and a versioned release bundle (13.1) exist; a change cannot merge without a score. **L3**: online evals, canaries and a feedback flywheel turn production traffic into new test items. **L4**: a governed multi-team platform with SLOs, cost attribution per tenant and audited change control. Maturity is per system, not per company: a regulated internal tool may need L4 governance while L1 release velocity is acceptable.

Name an owner for each of the four artefacts: model, prompt, index and guardrail policy. Roles: AI/application engineer (prompts, tools, evals), ML engineer (training, serving), platform/SRE (GPU pools, deployment, on-call), data and annotation lead (golden sets, labels), security (policy, red-teaming), domain expert (rubrics, adjudication) and product owner (acceptance and priorities). RACI for the three recurring events: a *release* is accountable to the application engineer, with SRE and security consulted; an *incident* is accountable to the on-call owner of the failing artefact, with product informed; an *evaluation-set change* is accountable to the data lead, with the domain expert consulted and the application engineer merely informed (otherwise the author grades their own homework).

| Topology | Fits when | Risk |
|---|---|---|
| Central platform team | few product teams, owned GPUs, heavy regulation | ticket queue, shadow projects |
| Embedded AI engineers | many teams, fast domain iteration | duplicated tooling, uneven quality |
| Hybrid with enabling team | 5+ teams | needs a clear paved-road contract |

Build order matters: eval before observability tooling, registry before canary. Traces nobody scores are cost without insight. Link back to Module 01 section 1.1 (why LLMOps is not MLOps with a bigger model) and the lifecycle in 1.2.

Edge cases. A one-person team skips L3 and L4 but keeps three non-negotiables: a golden set, version pinning and a kill switch (13.6). An acquired team with a different stack should have its artefacts mapped onto the four-artefact model first; forcing a migration before ownership is clear destroys the history you need.

### Cross-Connection Scenarios
- The release bundle (13.1) is the L2 artefact; the canary (13.3) is the L3 control.
- Eval ownership connects to judge calibration in Module 07 and annotation workflows in Module 02.
- Cost attribution at L4 depends on the per-tenant metering in Module 11.
- Incident roles map onto the runbooks in Module 10.

### Production Anti-Patterns
- Buying an observability suite before any eval set exists: traces accumulate that nobody scores, so quality never improves.
- No named prompt owner: changes arrive via chat, and nobody can answer "who changed this?" during an incident.
- A central AI team that becomes a ticket queue: product teams bypass it with shadow projects that have no controls.

### Minimal Working Code
The first block scores a capability checklist; a level is reached only if all lower levels are complete, and the output lists the highest-leverage gaps.

```python
LEVELS = {
    1: ["prompts_in_git", "basic_tracing"],
    2: ["golden_set", "ci_eval_gate", "release_bundle"],
    3: ["online_evals", "canary", "feedback_loop"],
    4: ["slos", "cost_attribution", "change_audit"],
}

def maturity(caps: dict):
    level = 0
    for lv in sorted(LEVELS):
        if all(caps.get(c, False) for c in LEVELS[lv]):
            level = lv
        else:
            break
    missing = [c for lv in sorted(LEVELS) for c in LEVELS[lv] if not caps.get(c, False)]
    return level, missing[:3]          # lowest-level gaps first = highest leverage

caps = {"prompts_in_git": True, "basic_tracing": True, "golden_set": True,
        "ci_eval_gate": False, "canary": True}
lvl, gaps = maturity(caps)
print(lvl, gaps)
assert lvl == 1 and gaps[0] == "ci_eval_gate"
```

The second block lints artefact ownership: missing owners, owner equal to reviewer, and bus-factor concentration.

```python
from collections import Counter

def lint_ownership(artefacts: dict, max_per_person: int = 3):
    issues = []
    for name, a in artefacts.items():
        if not a.get("owner"):
            issues.append(f"{name}: no owner")
        elif a.get("owner") == a.get("reviewer"):
            issues.append(f"{name}: owner == reviewer")
        if not a.get("oncall"):
            issues.append(f"{name}: no oncall")
    load = Counter(a["owner"] for a in artefacts.values() if a.get("owner"))
    for person, n in load.items():
        if n > max_per_person:
            issues.append(f"{person}: owns {n} artefacts (bus factor)")
    return issues

arts = {
    "model": {"owner": "asha", "reviewer": "ben", "oncall": "sre"},
    "prompt": {"owner": "asha", "reviewer": "asha", "oncall": "asha"},
    "index": {"owner": "", "reviewer": "ben", "oncall": "sre"},
    "policy": {"owner": "asha", "reviewer": "cy", "oncall": ""},
}
out = lint_ownership(arts, max_per_person=2)
print(*out, sep="\n")
assert "index: no owner" in out and "prompt: owner == reviewer" in out
```

### Interview Angle
**Q:** You join a team whose prompts live in application code and there are no evals. What do you do in the first 90 days? **A:** Month 1: measure a baseline, build a golden set of roughly 100 real items, pin model versions. Month 2: move prompts to a registry and sample traces. Month 3: add a CI gate with a non-inferiority margin. The trade-off is feature velocity versus safety; I accept slower merges for one quarter. Exit check: any PR is blocked or passed by a score with a confidence interval, and run-to-run noise is measured.

**Q:** Platform team versus embedded engineers for eight product teams? **A:** Hybrid: a small enabling team owns the paved road (registry, eval harness, gateway) and embedded engineers own prompts and domain evals. Central-only becomes a queue; embedded-only duplicates tooling. Measure time-to-first-eval for a new team and the share of services on the paved road; if adoption stays under about half, the platform is not useful and I would change the offer.

**Q:** Name three operational differences from classic MLOps. **A:** Behaviour is controlled by prompts and context, so they need versioning and review (registry). Outputs are open-ended, so you need graded evals instead of one accuracy number. Cost and latency scale with tokens per request, so you need per-request metering and budgets. Check: each control has an owner and a dashboard.

## 1.7 Build vs Buy vs Hybrid: Hosted API, Managed Open-Weight, Self-Hosted

### Conceptual Deep Dive
There are three consumption modes. A **proprietary hosted API** trades control for zero infrastructure. A **managed endpoint for open-weight models** (a cloud or inference provider serves weights you choose) gives model choice and some customisation with less operational load. **Self-hosting** on owned or rented GPUs gives maximum control and the highest fixed cost. A **hybrid** routes by sensitivity, volume and capability: regulated data to the self-hosted pool, spiky or frontier-capability work to the API. A build vs buy decision is therefore a routing policy, not a single choice.

Decision axes: data sensitivity and residency; traffic volume and utilisation (use the break-even maths from Module 11 section 2.3); latency and rate-limit headroom; customisation need (fine-tune, adapters); capability ceiling; team skills; lock-in and exit cost. The number that usually decides is **sustained utilisation**: a dedicated GPU is cheaper per token only when it is busy.

TCO items people forget: idle capacity, on-call and SRE time, eval and security review, upgrade and migration engineering, egress, redundancy (N+1 replicas), and the cost of a failure day. Add them as an ops-FTE fraction, not as zero.

A **provider abstraction** (chat, embed, tool-call schema normalisation behind a thin internal interface) turns switching into a configuration change. It leaks in predictable places: tokenisers (cost and truncation), tool-call formats, safety filters, and JSON-mode semantics. Contract-test every adapter (see the code below).

A staged strategy works well: start on the API, instrument unit economics, graduate stable high-volume workloads to self-host or managed open-weight, and keep the API for spiky or frontier work. Classify each choice as a two-way door (config flag) or one-way door (a fine-tune pipeline, a GPU contract) and record it in an ADR (12.7).

Edge cases. Traffic grows 10x in a quarter: the break-even moves toward dedicated, but GPU lead time and capacity quotas may be weeks, so keep an API burst path. A regulation or contract forces on-prem mid-flight: only the abstraction, the eval suite and portable prompts make that survivable. A new hosted model obsoletes your fine-tune: judge on forward cost and measured quality, not on the sunk training spend.

### Production Anti-Patterns

- Importing a provider SDK type into every service's domain layer: switching becomes a rewrite.
- Ignoring the provider's data-use and retention terms until legal asks: the fix then happens under pressure.

### Minimal Working Code
The first block compares API, dedicated and serverless monthly cost; every price is a placeholder (perishable).

```python
HOURS = 730  # hours per month

def api_cost(tokens, price_per_mtok):
    return tokens / 1e6 * price_per_mtok

def dedicated_cost(gpus, gpu_hour, ops_fte, fte_month):
    return gpus * gpu_hour * HOURS + ops_fte * fte_month

def compare(tokens, tps_per_gpu=1500, gpus=2, util_note=True):
    P = {"api": 5.0, "serverless": 3.0, "gpu_hour": 2.5, "fte_month": 15000}  # placeholders
    cap = gpus * tps_per_gpu * 3600 * HOURS
    ded = dedicated_cost(gpus, P["gpu_hour"], 0.2, P["fte_month"])
    out = {"api": api_cost(tokens, P["api"]),
           "serverless": api_cost(tokens, P["serverless"]),
           "dedicated": ded, "utilisation": tokens / cap}
    out["breakeven_tokens_vs_api"] = ded / P["api"] * 1e6
    return out

for t in (1e9, 2e10):
    r = compare(t)
    print({k: round(v, 3) for k, v in r.items()})
assert compare(2e10)["dedicated"] < compare(2e10)["api"] < compare(1e9)["api"] * 100
assert compare(1e9)["api"] < compare(1e9)["dedicated"]
```

The second block defines a provider protocol, a deterministic fake and a contract test every adapter must pass.

```python
from typing import Iterator, Protocol

class ChatProvider(Protocol):
    def chat(self, messages: list, max_tokens: int = 64) -> dict: ...
    def stream(self, messages: list, max_tokens: int = 64) -> Iterator[str]: ...

class FakeProvider:
    def chat(self, messages, max_tokens=64):
        words = ("echo " + messages[-1]["content"]).split()[:max_tokens]
        stop = "length" if len(words) == max_tokens else "stop"
        return {"text": " ".join(words), "stop_reason": stop,
                "usage": {"input_tokens": sum(len(m["content"].split()) for m in messages),
                          "output_tokens": len(words)}}
    def stream(self, messages, max_tokens=64):
        yield from self.chat(messages, max_tokens)["text"].split()

def contract_test(p: ChatProvider):
    msgs = [{"role": "user", "content": "hello there world"}]
    r = p.chat(msgs, max_tokens=2)
    assert r["stop_reason"] in {"stop", "length", "tool_use"}
    assert r["stop_reason"] == "length" and r["usage"]["output_tokens"] == 2
    assert set(r["usage"]) >= {"input_tokens", "output_tokens"}
    assert " ".join(p.stream(msgs, max_tokens=8)) == p.chat(msgs, max_tokens=8)["text"]
    return "ok"

print(contract_test(FakeProvider()))
```

### Interview Angle
**Q:** A CFO asks whether to move from a hosted API to self-hosting. Walk through the analysis. **A:** Collect monthly tokens by workload, then compute dedicated cost (GPUs, redundancy, ops FTE fraction) divided by the API price per token to get break-even tokens, and compare with measured sustained utilisation. Trade-off: lower unit cost against fixed cost, on-call and capability risk. The deciding number is utilisation at peak-plus-redundancy; if it is below roughly half, stay on API or managed endpoints. Revisit when traffic doubles.

**Q:** How do you keep lock-in from creeping in over 12 months? **A:** One internal interface, adapters with a shared contract test in CI, no provider types in domain code, and a quarterly "swap drill" that runs the golden set on a second provider. Leaks to check: tokeniser-dependent limits, tool-call format, JSON-mode behaviour, safety filters. Measurable: the drill passes within the quality margin and takes under a day of engineering.

**Q:** When is a managed open-weight endpoint the right middle path? **A:** When you need open-weight control (a fine-tune, residency, a pinned model) but traffic is too low or the team too small to keep GPUs busy and on-call. Trade-off: per-token price and less tuning control against zero fleet operations. Check utilisation and cost per successful task quarterly to see whether graduating to self-hosting pays.

## 1.8 Model Lifecycle: Selection, Pinning, Deprecation and Vendor Risk

### Conceptual Deep Dive
**Selection protocol.** Shortlist three to five candidates, run your task-specific eval (public leaderboards are a screening aid only: contamination and task mismatch make them unreliable for your workload), plot the quality-cost-latency **Pareto** frontier, and choose the cheapest model whose quality *lower confidence bound* clears the bar. Using the lower bound prevents choosing a model that merely got lucky on a small set. Ties on quality are broken by p95/p99 latency, cost, licence terms and regional availability, in that order of reversibility.

**Pin dated snapshots, never floating aliases**, in production, and record the resolved model id in every trace. A floating alias can change behaviour without any commit on your side (the silent-update incident in Module 10). A pinned snapshot makes an incident bisectable.

**Deprecation calendar.** Keep an inventory with an owner, snapshot, eval report and sunset date per model. Track provider sunset notices, open-weight licence changes and engine or kernel end-of-life. Plan the migration window backwards from the sunset: evidence pack, shadow run, canary, bake, removal (13.4).

**Fallback parity.** A fallback model must pass the same eval gates as the primary; "available" is not "acceptable". Run the golden set against the fallback on a schedule, because fallbacks silently rot.

**Capability regression on upgrade.** Newer is not uniformly better; tokeniser and chat-template changes alter both cost and behaviour (full playbook in 13.4). **Reasoning variants** change latency and cost structure through hidden reasoning tokens, so treat them as separate catalogue entries with their own evals (see 3.8).

| Inventory field | Why it exists |
|---|---|
| snapshot id | reproducibility and bisecting |
| owner | someone gets the deprecation email |
| eval_report | evidence the model passed the gate |
| sunset_date | drives the migration calendar |
| fallback_for | shows parity obligations |

Edge cases. A provider shortens a deprecation window to 30 days: the runbook is to freeze feature changes, run the shadow comparison immediately against the pre-qualified fallback, accept the best candidate that passes the safety and format gates even if not optimal, and schedule re-tuning afterwards. Two models tie on quality: prefer the one with the lower tail latency and the clearer exit path.

### Production Anti-Patterns
- Using a public benchmark rank as the selection decision: the model is tuned for the benchmark, not your task.
- Floating alias in production with no output-version logging: behaviour changes and nobody can tell when.
- A fallback model that was never evaluated: the failover fires during an outage and quality drops with no warning.

### Minimal Working Code
The first block checks a model inventory for models expiring soon or lacking an eval report.

```python
from dataclasses import dataclass
from datetime import date

@dataclass
class ModelRecord:
    id: str
    provider: str
    snapshot: str
    owner: str
    eval_report: str
    sunset_date: date | None

def audit(inv, today: date, within_days: int = 90):
    out = []
    for m in inv:
        if not m.eval_report:
            out.append((m.id, "no eval report"))
        if m.sunset_date and (m.sunset_date - today).days <= within_days:
            out.append((m.id, f"sunset in {(m.sunset_date - today).days} days"))
        if not m.owner:
            out.append((m.id, "no owner"))
    return out

inv = [ModelRecord("primary", "vendorA", "MODEL_ID-2025-01-01", "asha", "rep-12", date(2026, 3, 1)),
       ModelRecord("fallback", "vendorB", "MODEL_ID-b", "ben", "", None)]
res = audit(inv, today=date(2026, 1, 15))
print(res)
assert ("fallback", "no eval report") in res and any(r[0] == "primary" for r in res)
```

The second block selects the cheapest candidate whose confidence lower bound clears the target and reports the Pareto-dominated set.

```python
import numpy as np

def select(cands, target):
    # cands: name -> (q_mean, q_ci_low, cost, p95_latency)
    names = list(cands)
    M = np.array([[-cands[n][0], cands[n][2], cands[n][3]] for n in names])  # minimise all
    dominated = []
    for i in range(len(names)):
        for j in range(len(names)):
            if i != j and np.all(M[j] <= M[i]) and np.any(M[j] < M[i]):
                dominated.append(names[i])
                break
    ok = [n for n in names if cands[n][1] >= target]
    best = min(ok, key=lambda n: (cands[n][2], cands[n][3])) if ok else None
    return best, sorted(set(dominated))

c = {"small": (0.82, 0.78, 1.0, 0.9), "mid": (0.90, 0.87, 3.0, 1.4),
     "big": (0.92, 0.84, 9.0, 3.0), "old": (0.80, 0.70, 4.0, 2.0)}
best, dom = select(c, target=0.85)
print(best, dom)
assert best == "mid" and "old" in dom and "big" not in dom
```

### Interview Angle
**Q:** How do you choose between three candidate models for a customer-support assistant? **A:** Build a task eval from real tickets, score each candidate on quality, cost per resolved ticket and p95 latency, and compute confidence intervals with a paired bootstrap. Rule: choose the cheapest model whose quality lower bound clears the bar, with safety and format gates mandatory. Trade-off: a higher-quality model may not justify its cost. Check: the decision is reproducible from a stored eval report.

**Q:** A provider announces deprecation of the model behind your main feature. Give your six-week plan. **A:** Week 1: inventory dependants and shortlist replacements. Weeks 2-3: run the eval and a shadow comparison, re-tune prompts per model (3.7). Week 4: canary with guard metrics. Week 5: ramp and bake. Week 6: remove the old path after rollback is no longer needed. Check each gate with confidence intervals, and keep a pre-qualified fallback in case the window shrinks.

**Q:** Why are floating aliases dangerous and what do you log? **A:** The provider can change the underlying model without any change in your repository, so quality or cost shifts with no trace of cause. Pin dated snapshots and log the resolved model id, prompt version and bundle id on every request; run a small canary golden set daily. Alert when the resolved id changes or the canary score moves beyond its noise band.
