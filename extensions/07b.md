## 7.6 Pairwise Ranking and Rubric Judges: Bradley-Terry, Elo and Judge Ensembles

### Conceptual Deep Dive
Absolute scores ("rate this answer 1-10") saturate near the top, drift between judge versions and are poorly calibrated across prompts. **Pairwise** comparison is easier and more stable for a judge: show two answers to the same prompt and ask which is better. Aggregate with win rate, Elo, or **Bradley-Terry** maximum-likelihood strengths, where P(i beats j) = p_i / (p_i + p_j). Bradley-Terry is order-independent (Elo depends on game order), fits with a simple iterative minorise-maximise update, and supports bootstrap confidence intervals by resampling comparisons. The MT-Bench / Chatbot Arena paper (Zheng et al., 2023) is the standard reference for LLM-as-judge pairwise evaluation and its biases.

Known judge biases: **position** (preferring the first or second answer), **verbosity** (longer looks better), and **self-preference** (a judge favours outputs from its own model family). Mitigations: run every pair in both orders and count a verdict only when both agree (disagreements become ties); control length by instruction or by comparing on length-matched strata; use judges from a different family than the generators; and audit with human labels (14.2).

**Rubric decomposition** breaks "quality" into binary criteria: does it cite a source, answer the question asked, follow the format, avoid unsupported claims? Binary rubric items are more reliable than a holistic score, give actionable diagnosis (which criterion failed), and can be scored by cheaper judges. Vague criteria ("is it helpful?") are interpreted differently by different judges; write each as an observable test with examples.

Judge ensembles combine diverse judges by majority or mean, and route high-disagreement items to humans; a cost-aware cascade escalates only uncertain items (14.2). Sample size matters: with a true 55% win rate you need several hundred decisive comparisons for the interval to exclude 50%, and about 800 for roughly 80% power (rule of thumb from the normal approximation, verify for your setup). Adaptive pairing concentrates comparisons on close contenders instead of spreading them evenly. Handle ties explicitly: dropping them biases strengths toward overstated differences, so count a tie as half a win to each side or fit a model with a tie parameter. Non-transitive cycles (A beats B beats C beats A) are real on heterogeneous prompts and mean a single ranking is a simplification; report them.

Public arenas measure general chat preference on public users' prompts, which differs from your task and users; use them to shortlist, then run a private pairwise evaluation on your own traffic.

Edge cases: "both bad" outcomes carry no information about which is better but flag a quality problem, so keep them as a category; with few comparisons per pair the intervals are wide, and you must report them rather than a point estimate.

### Production Anti-Patterns
- Reporting a single Elo or win rate with no interval: differences inside the noise get shipped as wins.
- One judge, one ordering: position and self-preference bias go undetected.
- Rubrics with vague criteria that judges interpret differently: scores are unreproducible and unactionable.

### Minimal Working Code
Bradley-Terry strengths from (winner, loser) pairs via the MM algorithm, with bootstrap intervals and a ranking-stability report.

```python
import numpy as np

def bt_fit(pairs, n, iters=300, prior=0.5):
    W = np.zeros((n, n))
    for w, l in pairs:
        W[w, l] += 1
    W += prior * (1 - np.eye(n))                  # small pseudo-count keeps strengths finite
    N = W + W.T
    p = np.ones(n)
    for _ in range(iters):
        denom = (N / (p[:, None] + p[None, :])).sum(1)
        p = W.sum(1) / denom
        p /= np.exp(np.log(p).mean())             # fix the scale: geometric mean 1
    return p

rng = np.random.default_rng(0)
true = np.array([2.0, 1.4, 1.0, 0.5])
pairs = []
for _ in range(600):
    i, j = rng.choice(4, 2, replace=False)
    pairs.append((i, j) if rng.random() < true[i] / (true[i] + true[j]) else (j, i))

p = bt_fit(pairs, 4)
boots = np.array([bt_fit([pairs[k] for k in rng.integers(0, len(pairs), len(pairs))], 4) for _ in range(200)])
lo, hi = np.percentile(boots, [2.5, 97.5], axis=0)
orders = [tuple(int(i) for i in np.argsort(-b)) for b in boots]
top = max(set(orders), key=orders.count)
print("strengths", p.round(2))
for k in range(4):
    print(f"system {k}: {p[k]:.2f}  95% CI [{lo[k]:.2f}, {hi[k]:.2f}]")
print("most common ranking", top, "frequency", orders.count(top) / len(orders))
```

A position-debiased pairwise runner: the injectable judge is called twice with swapped order, win rate is computed only on consistent verdicts, and position bias is reported.

```python
import random

def run_pairs(items, judge):
    """items: (prompt, a, b). judge(prompt, first, second) -> 'first' | 'second' | 'tie'."""
    wins = {"a": 0, "b": 0}
    stats = {"consistent": 0, "ties": 0, "inconsistent": 0, "same_position": 0}
    for prompt, a, b in items:
        v1 = judge(prompt, a, b)
        v2 = judge(prompt, b, a)
        c1 = {"first": "a", "second": "b", "tie": "tie"}[v1]
        c2 = {"first": "b", "second": "a", "tie": "tie"}[v2]
        if c1 == c2 == "tie":
            stats["ties"] += 1
        elif c1 == c2:
            wins[c1] += 1
            stats["consistent"] += 1
        else:
            stats["inconsistent"] += 1
            stats["same_position"] += v1 == v2 != "tie"
    decisive = wins["a"] + wins["b"]
    return (wins["a"] / decisive if decisive else None), stats

rng = random.Random(0)
def fake_judge(prompt, first, second):           # prefers longer text but is biased to the first slot
    score = (len(first) - len(second)) / 20 + 0.6
    if abs(score) < 0.15:
        return "tie"
    return "first" if rng.random() < 1 / (1 + 2.718 ** (-score)) else "second"

items = [("q", "x" * rng.randint(5, 40), "y" * rng.randint(5, 40)) for _ in range(300)]
rate, stats = run_pairs(items, fake_judge)
print("win rate of A on consistent verdicts:", round(rate, 3), stats)
```

### Interview Angle
**Q:** You have two prompt variants and no ground truth. How do you decide which is better? **A:** Sample real inputs, generate with both, run an order-swapped pairwise judge from a different model family, plus a binary rubric for failure diagnosis, then audit a human-labelled subset. Report win rate over consistent verdicts with a bootstrap interval and add latency and cost. Trade-off: judge bias versus labelling cost. Check: the human-agreement rate on 100 items and an interval excluding 50%.

**Q:** How many comparisons do you need to separate two systems with a 55% win rate? **A:** About 385 decisive comparisons give a 95% interval half-width of 5 points, and roughly 800 give about 80% power to detect 55% versus 50% (normal approximation; ties and clustering by prompt increase it). Adaptive pairing and paired prompts reduce the need. Check: bootstrap intervals over prompts, not just comparisons.

**Q:** How do you detect and mitigate self-preference bias in an LLM judge? **A:** Compare judge preference for its own family's outputs against human labels on blinded pairs; a gap beyond noise indicates bias. Mitigate with cross-family judges or an ensemble, anonymised style, and length control. Trade-off: cost and agreement variance. Check: the win-rate gap between same-family and other-family outputs shrinks toward the human-labelled gap.

## 7.7 Error Analysis Workflow: Attributing Failures Across Retrieval, Prompt and Model

### Conceptual Deep Dive
Dashboards say that quality is low; **error analysis** says why. Start by reading 50-100 failing traces yourself and labelling each with a short free-text cause (open coding). Cluster those labels into a **failure taxonomy**, then count frequency, severity and fixability per category. The largest bucket of fixable, high-severity failures tells you where to work next; skipping the reading and tuning the prompt is the most common way to waste a sprint.

For RAG the attribution tree has a natural order: (1) the gold chunk is missing from the corpus (a content problem, not an engineering one); (2) it exists but was not retrieved in the top-k (recall); (3) it was retrieved but ranked below the context cutoff or cut by truncation (ranking and context assembly); (4) it was in context but the model ignored or contradicted it (unfaithful generation); (5) the model refused wrongly (over-refusal); (6) the answer is right but the format is broken; (7) the question was ambiguous. Each branch has different owners and fixes, so attribution comes before remediation.

**Counterfactual probes** isolate causes. The **oracle-context** test inserts the known-gold chunk(s) and re-asks: if the answer becomes correct, retrieval was the bottleneck; if it stays wrong, the problem is generation or the question. The no-context test removes retrieval: if the model answers correctly anyway, the case does not measure retrieval and may leak parametric knowledge. A shuffled-context test (same chunks, different order, or with distractors) exposes position sensitivity and distractor vulnerability.

Compute stage metrics alongside: retrieval recall@k, rerank hit rate, faithfulness, answer correctness. The product of stage success rates should roughly reproduce end-to-end accuracy; if it does not, your attribution is leaky. Failures with multiple causes get a primary and secondary label. Annotator disagreement on causes is normal: double-label a subset, measure agreement (14.3), and tighten category definitions.

Make it a loop: every fixed failure becomes a regression item in the golden set (14.4), and the taxonomy is re-labelled periodically because fixing the top bucket changes the distribution (the new top bucket is the next problem). Keep the taxonomy documented with an example for each category so new team members label consistently.

Edge cases: when a failure has several necessary causes (retrieval partly missed and the model is also weak), estimate upside with the oracle experiment rather than adding bucket shares, and expect fixes to overlap.

- Optimising average metrics instead of the biggest error bucket: effort lands where the gain is smallest.
- Skipping raw trace reading and relying on dashboards: aggregated scores hide the actual failure mechanisms.

### Minimal Working Code
A stage-attribution report from a results table, producing a Pareto of failure causes and the upside (accuracy points) of fixing each.

```python
from collections import Counter

def cause(r, k_ctx=5):
    if r["answer_correct"]:
        return None
    if not r["gold_in_corpus"]:
        return "corpus_gap"
    if not r["retrieved_gold"]:
        return "retrieval_miss"
    if r["rank"] > k_ctx:
        return "ranked_below_cutoff"
    if not r["correct_with_oracle"]:
        return "model_cannot_answer"
    if not r["faithful"]:
        return "ignored_context"
    return "other_format_or_ambiguity"

def pareto(rows):
    c = Counter(x for x in map(cause, rows) if x)
    total_fail, n, cum = sum(c.values()), len(rows), 0
    print(f"accuracy {1 - total_fail / n:.2%} over {n} items")
    for name, cnt in c.most_common():
        cum += cnt
        print(f"{name:26s} {cnt:3d}  share {cnt / total_fail:5.1%}  cum {cum / total_fail:5.1%}  upside +{cnt / n:.1%}")

rows = (
    [dict(answer_correct=True, gold_in_corpus=True, retrieved_gold=True, rank=1, correct_with_oracle=True, faithful=True)] * 70
    + [dict(answer_correct=False, gold_in_corpus=True, retrieved_gold=False, rank=99, correct_with_oracle=True, faithful=True)] * 14
    + [dict(answer_correct=False, gold_in_corpus=True, retrieved_gold=True, rank=8, correct_with_oracle=True, faithful=True)] * 5
    + [dict(answer_correct=False, gold_in_corpus=True, retrieved_gold=True, rank=2, correct_with_oracle=True, faithful=False)] * 7
    + [dict(answer_correct=False, gold_in_corpus=False, retrieved_gold=False, rank=99, correct_with_oracle=False, faithful=True)] * 4
)
pareto(rows)
```

TF-IDF plus a small k-means (best of several restarts) over failure descriptions to propose taxonomy buckets, printing the top terms per cluster.

```python
import numpy as np

docs = ["answer cites wrong policy document", "wrong policy retrieved for question", "no relevant document retrieved",
        "retrieved irrelevant policy page", "answer ignores provided context and invents numbers",
        "model invents figures not in context", "hallucinated number contradicts context",
        "output format broken json missing field", "invalid json schema field missing", "response not valid json",
        "wrong document retrieved for policy", "numbers invented despite context"]
tok = [d.split() for d in docs]
vocab = sorted({w for t in tok for w in t})
ix = {w: i for i, w in enumerate(vocab)}
tf = np.zeros((len(docs), len(vocab)))
for i, t in enumerate(tok):
    for w in t:
        tf[i, ix[w]] += 1
idf = np.log((1 + len(docs)) / (1 + (tf > 0).sum(0))) + 1
X = tf * idf
X /= np.linalg.norm(X, axis=1, keepdims=True)
rng = np.random.default_rng(0)

def kmeans(X, k, it=20):
    C = [X[rng.integers(len(X))]]
    while len(C) < k:                                    # k-means++ seeding
        d = np.min([((X - c) ** 2).sum(1) for c in C], axis=0)
        C.append(X[rng.choice(len(X), p=d / d.sum())])
    C = np.array(C)
    for _ in range(it):
        lab = np.argmin(((X[:, None] - C[None]) ** 2).sum(2), axis=1)
        C = np.array([X[lab == j].mean(0) if (lab == j).any() else C[j] for j in range(k)])
    return lab, C

best = None
for _ in range(8):
    lab, C = kmeans(X, 3)
    inertia = ((X - C[lab]) ** 2).sum()
    if best is None or inertia < best[0]:
        best = (inertia, lab, C)
_, lab, C = best
for j in range(3):
    print(j, int((lab == j).sum()), [vocab[i] for i in np.argsort(-C[j])[:4]])
```

### Interview Angle
**Q:** Users complain about wrong answers. Give your process to find out why in two days. **A:** Day 1: pull 100 recent negative-feedback or low-score traces, read them, label causes, and build the taxonomy with frequencies. Day 2: run oracle-context and no-context probes on a 50-item sample to split retrieval from generation, then present a Pareto with estimated upside per bucket and one proposed fix for the top bucket. Trade-off: speed versus sample size. Check: two labellers agree on a 20-item subset.

**Q:** How do you know whether to fix retrieval or generation first? **A:** Oracle-context accuracy versus end-to-end accuracy. If giving the gold chunk lifts accuracy a lot, retrieval (recall, ranking, chunking) holds most of the upside; if accuracy stays low even with the gold chunk, work on prompt, model or question quality. Check retrieval recall@k and faithfulness separately, and fix the stage with the larger error mass.

**Q:** What is an oracle-context experiment and what does it tell you? **A:** Replace retrieval with the known-gold evidence and re-run generation. The accuracy gain is the upper bound of what better retrieval can deliver; the remaining gap is generation, ambiguity or label errors. Limitations: gold chunks may be incomplete for multi-hop questions, and it ignores latency and cost of better retrieval. Report it with an interval over the item set.
