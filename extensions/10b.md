## 10.6 GenAI Telemetry Design: Semantic Conventions, Content Capture and Sampling Policy

### Conceptual Deep Dive
OpenTelemetry's GenAI **semantic conventions** standardise span and metric attributes for model calls (operation name, requested and response model, token usage, finish reasons). They are still evolving (status "development" at the time of writing; verify against the current spec). Names have moved: early drafts used `gen_ai.system` for the provider and carried prompt and completion text as span attributes (`gen_ai.prompt`, `gen_ai.completion`, which the legacy chapter's examples use); later revisions renamed the provider attribute and moved message content into events or opt-in attributes. Design your telemetry layer so attribute names are defined in one mapping module and can be switched with a config flag, and keep a dual-emit period when migrating dashboards.

**Span hierarchy** that reconstructs an agent run: request, guardrail, retrieval, agent step, LLM call, tool call. Put retrieval results (document ids and scores, not text) and the prompt/bundle id on spans so a bad answer can be traced to the exact configuration. **Content capture** is opt-in: always record metadata (token counts, model, finish reason, latency, TTFT), and record prompt or completion text only under an explicit policy, redacted at the collector so applications cannot bypass it (8.7).

**Tail sampling** decides after the trace completes: keep every error, slow, expensive and low-judge-score trace plus a small random baseline chosen by hashing the trace id so all services agree. Head sampling at a fixed rate throws away the interesting traces before you know they are interesting.

**Cardinality discipline.** Metric labels should be bounded sets: model, route, tenant tier, outcome. User ids and prompt hashes go on spans, not on Prometheus labels. Use **exemplars** to attach a trace id to a histogram bucket so an engineer can jump from a latency spike to a concrete trace. Link feedback and eval items to trace ids so production failures become eval cases (14.4).

Edge cases. Async boundaries (queues, background workers, tool callbacks) drop context unless the trace context is propagated explicitly in message headers. Streaming responses: record TTFT as an event on the span; close the span when the stream ends or the client disconnects, otherwise spans leak or report impossible durations.

### Cross-Connection Scenarios
- Privacy-safe content capture and redaction (8.7).
- Quality SLIs computed from sampled traces (10.7).
- Trace-id linkage to evaluation datasets (14.4).
- Per-tenant cost attribution from token metrics (11.8).

### Production Anti-Patterns
- Sampling at 1% head-based and then wondering where the incident traces are.
- Storing full prompts in span attributes by default: every trace backend user can read customer data and storage cost balloons.
- Per-user labels on Prometheus metrics: series count explodes and the monitoring system degrades or bills unexpectedly.

### Minimal Working Code
A tail-sampling decision function (error, latency, cost, judge score, baseline probability by trace-id hash) and a simulation reporting the kept fraction and the recall of bad traces versus head sampling.

```python
import hashlib, random

def baseline_hit(trace_id, p):
    h = int(hashlib.sha256(trace_id.encode()).hexdigest()[:8], 16) / 2**32
    return h < p

def keep(t, slow_ms=4000, cost_cap=0.05, low_score=0.5, p=0.02):
    if t["error"] or t["latency_ms"] > slow_ms or t["cost"] > cost_cap:
        return True
    if t["judge"] is not None and t["judge"] < low_score:
        return True
    return baseline_hit(t["id"], p)

random.seed(0)
traces = []
for i in range(20000):
    bad = random.random() < 0.05
    judged = random.random() < 0.3                     # judge sees only some traffic
    traces.append({"id": f"t{i}", "bad": bad,
                   "error": bad and random.random() < 0.3,
                   "latency_ms": random.gauss(1500, 400) + (3000 if bad and random.random() < 0.2 else 0),
                   "cost": 0.01 if not bad else random.choice([0.01, 0.2]),
                   "judge": (0.2 if bad else 0.9) if judged else None})

kept = [t for t in traces if keep(t)]
bad_total = sum(t["bad"] for t in traces)
recall = sum(t["bad"] for t in kept) / bad_total
head = [t for t in traces if baseline_hit(t["id"], len(kept) / len(traces))]
head_recall = sum(t["bad"] for t in head) / bad_total
print(f"kept {len(kept)/len(traces):.3f} tail_recall {recall:.3f} head_recall {head_recall:.3f}")
assert recall > head_recall + 0.2
```

A span-attribute sanitiser: allow-list keys, truncate long values, hash high-cardinality fields, and drop content unless a capture flag is set.

```python
import hashlib

ALLOW = {"gen_ai.request.model", "gen_ai.usage.input_tokens", "gen_ai.usage.output_tokens",
         "route", "tenant_tier"}
HASH = {"user.id", "session.id"}
CONTENT = {"prompt", "completion"}

def sanitise(attrs, capture_content=False, max_len=200):
    out = {}
    for k, v in attrs.items():
        if k in ALLOW:
            out[k] = v
        elif k in HASH:
            out[k] = hashlib.sha256(str(v).encode()).hexdigest()[:12]
        elif k in CONTENT and capture_content:
            out[k] = str(v)[:max_len]
        # everything else is dropped
    return out

raw = {"gen_ai.request.model": "MODEL_ID", "gen_ai.usage.input_tokens": 120, "user.id": "alice@example.com",
       "prompt": "my card is 4111 ...", "completion": "x" * 500, "debug.secret": "token"}
safe = sanitise(raw)
assert "prompt" not in safe and "debug.secret" not in safe
assert len(safe["user.id"]) == 12 and safe["user.id"] != "alice@example.com"
with_content = sanitise(raw, capture_content=True)
assert len(with_content["completion"]) == 200
print(safe)
```

### Interview Angle
**Q:** Design tracing for a multi-step agent so an engineer can reconstruct a bad run without exposing PII.
**A:** One trace per request with child spans per agent step, LLM call and tool call; spans carry ids, scores, token counts, tool names and argument shapes, with content captured only under a policy flag and redacted at the collector. Trade-off: less content means slower debugging, so enable sampled capture for flagged traces with short retention. Check: engineers resolve a seeded incident from traces alone, and a PII scan of stored spans finds none.

**Q:** How do you keep trace storage affordable while retaining the incident traces?
**A:** Tail sampling: keep all errors, slow, expensive and low-score traces plus a hash-based baseline, and drop or shorten retention for the rest. Cost: a buffering collector tier that holds traces until completion. Check: recall of known-bad traces (from user reports) in the kept set stays near 100% and the kept fraction stays within storage budget.

**Q:** What do you do when the semantic conventions change under you?
**A:** Isolate attribute names in one mapping layer, dual-emit old and new names during migration, pin the instrumentation version, and update dashboards and alerts from the mapping. Trade-off: temporary duplicate cost. Check: a contract test asserting emitted attributes match the chosen spec version, and no dashboard panel going empty after cutover.

## 10.7 Quality SLOs and Alerting for Non-Deterministic Systems

### Conceptual Deep Dive
Latency and error SLOs are necessary but do not tell you whether answers are good. Define **quality SLIs** as proportions measured on sampled traffic: judged-correct rate, groundedness, format validity, refusal rate, task success, explicit feedback rate, and success of synthetic canary probes with known answers. Each is a proportion, so each fits the standard SLO machinery: a target (for example 95% judged-correct over 28 days), a windowed measurement and an **error budget** equal to the allowed bad fraction.

Judge-based SLIs are noisy and sampled, so alert logic must be confidence-aware. Use Wilson bounds on the bad proportion and a **minimum sample** size before any alert can fire; an alert on 7 of 10 sampled responses failing is not evidence. Multi-window burn-rate alerts (a fast window and a slow window both over threshold) reduce flapping while catching real regressions. Burn rate is the observed bad rate divided by the budgeted bad rate.

**Change detection** complements thresholds. After a deploy, compare the new bundle with the previous one on the same segments. For slow drift, run CUSUM or Page-Hinkley on judge scores: they accumulate small persistent deviations and detect shifts that no single window crosses. Compare within segments (language, route, tenant tier) to avoid Simpson effects, where a traffic mix change moves the aggregate without any per-segment change.

**Alert hygiene.** Page for user-visible breaches with fast burn; open tickets for slow burns; every alert links a runbook (check release markers, bundle diff, provider status, judge health); deduplicate and group by cause. **Provider incident correlation:** canary probes against a pinned prompt and the provider status feed help separate your regression from the provider's. Dashboards need release markers, the bundle id, and per-segment quality panels.

Edge cases. Low-traffic tenants never reach the minimum sample, so aggregate them into cohorts or use long windows. A judge outage produces missing data, which looks like "no bad answers"; alert on missing data (sample count below expected) as a separate condition.

### Cross-Connection Scenarios
- Telemetry and trace sampling feeding SLIs (10.6).
- Judge calibration and drift (14.2).
- Release gates and rollback triggers (Module 03, 14.4).
- Incident response and post-mortems (Module 12).

### Production Anti-Patterns
- Paging on a noisy 5-minute judge average: operators learn to ignore the pager.
- No minimum sample size: small-n fluctuations create false pages and false confidence.
- Quality alerts without release markers: responders cannot tell whether a deploy caused the drop.

### Minimal Working Code
A burn-rate calculator over multiple windows using Wilson bounds and a minimum-sample guard.

```python
import math

def wilson_bounds(bad, n, z=1.96):
    p = bad / n
    d = 1 + z * z / n
    c = (p + z * z / (2 * n)) / d
    h = z * math.sqrt(p * (1 - p) / n + z * z / (4 * n * n)) / d
    return max(0.0, c - h), min(1.0, c + h)

def burn_alert(windows, slo=0.95, threshold=2.0, min_n=100):
    """windows: list of (bad, n). Fire only if every window has enough samples and its lower bound burns fast."""
    budget = 1 - slo
    rates = []
    for bad, n in windows:
        if n < min_n:
            return {"fire": False, "reason": "insufficient_samples"}
        lo, _ = wilson_bounds(bad, n)
        rates.append(lo / budget)
    return {"fire": all(r > threshold for r in rates), "burn": [round(r, 2) for r in rates]}

print(burn_alert([(30, 200), (150, 1500)]))             # sustained
print(burn_alert([(8, 10), (150, 1500)]))               # tiny fast window
assert burn_alert([(30, 200), (400, 1500)])["fire"]
assert burn_alert([(8, 10), (400, 1500)])["reason"] == "insufficient_samples"
assert not burn_alert([(10, 200), (75, 1500)])["fire"]
```

A CUSUM detector on a simulated stream of judge scores with a mean shift, reporting detection delay versus false-alarm rate for several thresholds.

```python
import numpy as np

def cusum_alarm(x, mu0, k, h):
    s = 0.0
    for i, v in enumerate(x):
        s = max(0.0, s + (mu0 - v - k))        # one-sided: detects a drop
        if s > h:
            return i
    return None

rng = np.random.default_rng(0)
sigma, change, T, runs = 0.05, 150, 300, 300
res = {}
for h in (0.1, 0.2, 0.4):
    false_alarms, delays = 0, []
    for _ in range(runs):
        x = np.concatenate([rng.normal(0.85, sigma, change), rng.normal(0.80, sigma, T - change)])
        i = cusum_alarm(x, mu0=0.85, k=0.5 * sigma, h=h)
        if i is None:
            continue
        if i < change:
            false_alarms += 1
        else:
            delays.append(i - change)
    res[h] = (false_alarms / runs, float(np.mean(delays)) if delays else float("nan"))
    print(f"h={h}: false_alarm_rate={res[h][0]:.2f} mean_delay={res[h][1]:.1f}")
assert res[0.1][0] >= res[0.4][0]
assert res[0.4][1] >= res[0.1][1]
```

### Interview Angle
**Q:** How do you define and alert on "answer quality" for a production assistant?
**A:** Define SLIs as proportions: judged-correct on a calibrated sample, groundedness, format validity, and canary-probe success, with a target and error budget. Alert on multi-window burn rate with Wilson bounds and a minimum sample; page only on user-visible fast burn. Trade-off: judge cost and noise versus coverage. Check: replay historical incidents and confirm detection within the target time with an acceptable false-page count.

**Q:** Quality dropped silently for two days. What monitoring was missing?
**A:** Likely candidates: no sampled quality SLI, alerts on infrastructure metrics only, judge outage treated as no data, no drift detector (CUSUM) for slow decline, no release markers, and no per-segment panels. I would add each with a runbook. Check: inject a synthetic degradation in staging and measure time-to-detect; require it under the agreed bound.

**Q:** How do you avoid alert fatigue from LLM-judge metrics?
**A:** Use confidence bounds and minimum samples, burn-rate windows rather than raw averages, page only on user-visible breaches, route slow burns to tickets, group duplicate alerts and prune alerts nobody acts on. Trade-off: slower detection of small regressions. Check: pages per week, fraction of pages that led to action, and median time-to-acknowledge.
